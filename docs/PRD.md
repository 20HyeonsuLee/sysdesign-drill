# PRD: 시스템 설계 꼬리질문

| 항목 | 값 |
|---|---|
| 상태 | 초안, 2026-10-21 |
| 버전 | v1 운영 중, v2 설계 중 |
| 함께 읽을 문서 | [ARD](ARD.md): 구조와 결정 |

- 모범 답과 해설은 이 문서에 쓰지 않는다. 문서를 읽다가 답을 보게 되기 때문이다.
- 문제를 설명할 때도 해법 이름을 쓰지 않는다.

## 1. 한 줄 정의

시스템 설계 답안을 코딩테스트처럼 채점하는 면접 연습장이다. 설계를 블록으로 쌓으면 채점기가 동시 실행과 장애를 모두 펼쳐 보고, 통과와 실패, 가장 짧은 반례를 돌려준다.

## 2. 풀려는 문제

- 백엔드 면접의 설계 꼬리질문이 보는 것은 세 가지다.
  1. 상황에서 지켜야 할 규칙을 세우는가
  2. 그 규칙을 깨는 장애를 스스로 떠올리는가
  3. 깨지지 않는 설계를 고르고, 수치와 내부 동작으로 근거를 대는가
- 코딩테스트는 채점기가 있어서 혼자 풀어도 맞았는지 안다. 설계에는 채점기가 없다. 혼자 공부하면 모범 답을 읽고 수긍하는 데서 끝난다.
- 읽어서 아는 것과 면접장에서 스스로 떠올리는 것은 다르다. 지금은 그 차이를 잴 방법이 없다.
- 그래서 이 제품의 본질은 **설계 답안 채점기**다. 채점기가 있어야 놓친 장애를 반례로 보고, 같은 유형을 반복해 풀고, 숙달을 숫자로 판단한다.

## 3. 사용자

- 백엔드 신입 면접을 준비하는 한 명(저장소 주인)이다. 다른 사용자는 고려하지 않는다.
- 노트북에서 주로 풀고, 이동 중에는 휴대폰으로 푼다.
- JD 단골 주제 네 가지를 대비한다: 대규모 트래픽, 대규모 데이터, 외부 API 연동, 데이터 정합성.

## 4. 목표 역량: "체화"의 정의

원문 요구 5(엣지케이스를 하나씩 따지다가 숙달되면 추상화해서 빠르게 푼다)를 잴 수 있는 단계로 나눈다.

| 단계 | 할 수 있는 것 | 주어지는 것 | 연습 모드 |
|---|---|---|---|
| 1. 고치기 | 반례를 보고 설계를 고친다 | 규칙, 테스트 목록, 반례 | 입문 |
| 2. 내다보기 | 반례를 보기 전에 깨지는 경우를 떠올린다 | 규칙, 테스트 개수 | 중급 |
| 3. 세우기 | 상황만 보고 규칙과 장애 모델을 스스로 세운다 | 상황 | 실전 |

- 면접이 요구하는 것은 3단계다. 시간 제한이 있고, 말로 설명해야 한다.
- 추상화했다는 것은 처음 보는 도메인의 문제를 보고 이미 겪은 실패 유형임을 알아보는 것이다. 그래서 숙달은 문제가 아니라 **실패 유형** 단위로, **처음 보는 문제**에서 잰다.
- 같은 문제를 다시 풀어 통과한 것은 기억이지 추상화가 아니다. 복습으로 세되 체화 판정에는 넣지 않는다.

## 5. 원문 요구 (바꾸지 않는다)

1. 문제는 꼬리에 꼬리를 무는 형태다.
2. 구체적인 코드는 쓰지 않는다. 면접에서 코드를 짜지 않는다.
3. 답은 아키텍처 설계, 트랜잭션 설계 수준이다.
4. 답을 정량적으로 검증한다. 알고리즘 코딩테스트처럼 통과와 실패가 나와야 한다.
5. 처음에는 엣지케이스를 하나씩 따지느라 오래 걸리고, 숙달되면 추상화해서 빠르게 푼다. 그 수준까지 가는 게 목표다.

사용자가 정한 것 (2026-10-21)

| 항목 | 결정 |
|---|---|
| 서술형 채점 | AI 채점 없음. 모범 답과 나란히 놓고 스스로 비교한다 |
| 배포 | GitHub Pages, 공개 저장소 |
| 개인 프로젝트와 같은 유형의 문제 | 내도 된다 |

## 6. 근본 요구

원문 요구에서 끌어낸 요구다. 7절의 기능은 이 요구를 채우는 수단이다. 기능을 바꿀 때는 이 표를 기준으로 판단한다.

### 6.1 채점

| ID | 요구 | 원문 | 확인 방법 |
|---|---|---|---|
| N1 | 같은 답은 언제나 같은 결과를 받는다. 사람이나 AI의 판단이 끼지 않는다 | 4 | 같은 답을 두 번 제출하면 결과와 반례가 같다 |
| N2 | 통과의 뜻을 문제마다 적는다. 통과는 "적어 둔 세계 모델과 장애 예산 안에서, 가능한 모든 실행 순서에 대해 규칙을 지킨다"는 뜻이다 | 4 | 문제 화면에 세계 모델과 모델링하지 않은 것이 보인다 |
| N3 | 틀린 설계가 통과하면 안 된다(거짓 통과). 틀린 모델을 체화하게 만들기 때문에 가장 나쁜 결함이다 | 4, 5 | 대표 오답이 하나라도 통과하면 출제하지 않는다. 엔진이 못 보는 장애는 다른 단계에서 묻거나 경계로 적는다 |
| N4 | 맞는 설계가 실패하면 안 된다(거짓 실패). 정답이 여러 갈래면 모두 통과한다 | 4 | 접근이 다른 모범 답을 가능하면 2개 두고 모두 통과시킨다 |
| N5 | 실패는 배울 수 있는 모양으로 돌려준다. 깨진 규칙 문장과 가장 짧은 반례를 보여 주고, 길이가 같으면 장애가 적은 반례를 먼저 보여 준다 | 5 | 반례 길이의 최소성을 탐색 방식이 보장한다 |
| N6 | 규칙은 안전(나쁜 일이 생기지 않는다)과 진행(장애가 없으면 일이 끝난다)을 둘 다 갖는다. 아무것도 안 하는 설계는 통과하지 못한다 | 4 | 단계마다 진행 규칙이 하나 이상 있다 |

### 6.2 문제 형태

| ID | 요구 | 원문 | 확인 방법 |
|---|---|---|---|
| N7 | 답의 단위는 면접에서 말로 하는 한 단계다. 기본 동작, 트랜잭션 경계, 외부 호출의 결과별 갈래로 답한다. 코드는 없다 | 2, 3 | 블록 목록에 코드 입력이 없다 |
| N8 | 답의 재료가 답을 알려 주면 안 된다. 블록에는 기본 동작만 두고 패턴 이름을 쓰지 않는다. 답을 가르는 선택에는 기본값이 없다 | 4, 5 | 블록 이름 검토, 답을 가르는 선택지가 빈 채로 시작한다 |
| N9 | 꼬리질문은 내 답에서 이어진다. 다음 단계는 내가 통과시킨 설계를 이어받고, 수치 정답도 그 설계로 계산한다 | 1 | 설계를 바꾸면 수치 정답이 바뀐다 |
| N10 | 꼬리질문은 면접관이 파고드는 순서를 따른다: 기본 → 실패 → 규모 → 설정값 → 내부 | 1, 3 | 문제마다 5단계 |
| N11 | 수치 문항은 답이 하나로 정해진다. 계산 규칙(무엇이 커넥션을 쥐는지 등)을 문제에 적고, ±10%를 정답으로 본다 | 4 | 계산 규칙만 보고 정답을 하나로 낼 수 있다 |

### 6.3 학습

| ID | 요구 | 원문 | 확인 방법 |
|---|---|---|---|
| N12 | 고민할 시간을 보장한다. 단계를 처음 연 뒤 일정 시간 힌트와 포기를 잠근다. 해설은 통과하거나 포기한 뒤에만 연다 | 5 | 잠금 중 힌트 버튼이 동작하지 않는다 |
| N13 | 비계를 단계별로 걷는다: 테스트 공개 → 테스트 숨김 → 규칙 숨김(4절) | 5 | 모드 세 가지 |
| N14 | 숙달은 실패 유형별로 잰다. 표본은 "처음 푼 문제의 첫 제출"이다. 같은 문제를 다시 푼 기록은 복습으로 따로 센다 | 5 | 문제 하나만으로는 체화 판정이 나지 않는다 |
| N15 | 문제 은행은 실패 유형 × 도메인 표로 채운다. 유형마다 도메인이 다른 문제가 2개 이상 있어야 N14를 잴 수 있다 | 5 | 유형별 문제 수 표 |
| N16 | 면접은 말로 끝난다. 흐름 단계를 통과하면 "면접에서 말로 하면" 문단을 내가 먼저 쓰고 모범과 나란히 본다 | 1, 3 | 작성란과 비교 화면 |
| N17 | 속도를 잰다. 단계별 소요 시간을 남기고, 실전 모드는 제한 시간을 건다 | 5 | 기록에 소요 시간이 있다 |

## 9. 범위 밖

- AI 채점, 코드 작성과 실행

- 실제 DB나 브로커를 띄워 돌리는 검증
- 여러 사용자, 기기 간 기록 동기화

문제 2: 회원가입 뒤 계좌 자동 개설

- 회원 서비스와 계좌 서비스의 DB가 나뉘어 있다.
- 다루는 실패: 회원은 생겼는데 계좌가 없다, 계좌가 두 개 생긴다, 이벤트가 사라진다.
- L3은 소비자 처리량과 파티션 수, L4는 재시도 간격과 폴링 주기, L5는 소비 확인 시점과 파티션 키에 따른 순서를 묻는다.

| 주제 | 후보 |
|---|---|
| 데이터 정합성 | 재고 N개 동시 차감, 계좌 이체(두 행 동시 갱신) |
