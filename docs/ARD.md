## 2. 구성

```text
src/engine.js          채점 엔진: 세계 선언 해석, 블록 트리 컴파일, 상태 공간 탐색, 점유 시간 측정
src/problems/<id>.js   문제: 상황, 세계, 규칙 함수, 단계, 테스트, 블록 재료, 힌트, 해설, 대표 오답
app/                   화면: 템플릿, 스타일, 블록 편집기(문제의 재료로 그린다), 반례 표, 기록
test/validate.js       검수: 형식, 모범 답 전부 통과, 대표 오답은 기대한 테스트에서만 실패
test/engine-smoke.js   엔진 기능 점검: 자원 종류별 작은 세계
test/browser-check.js  헤드리스 화면 점검: 모든 모범 답과 오답을 화면에 넣어 채점, 390px 넘침, 콘솔 오류
test/leak-check.js     답 노출과 문체 점검: 답을 흘리면 안 되는 칸의 해법 이름, 금지 문체
AUTHORING.md           문제 작성 지침(세계, 블록, 재료, 테스트, 규칙 함수의 계약)
research/              유형 전수조사, 출제 브리프
build.py               엔진, 문제, 화면을 인라인 스크립트로 묶어 HTML 한 파일을 만든다
index.html             빌드 결과. GitHub Pages가 내보낸다
```

- 지금 이 저장소에는 `index.html`과 문서만 있다. 원본은 저장소 밖 작업 폴더에 있다(AD-8).

채점 흐름

1. 사용자가 단계의 흐름마다 블록 트리를 쌓는다(요청 흐름, 배경 흐름, 소비 흐름).
2. 엔진이 블록 트리를 점프가 있는 명령 배열로 컴파일한다. 갈래가 있는 블록(외부 호출, 변경, 넣기, 발행, 조건, 캐시 읽기)은 갈래마다 점프 대상을 갖는다.
3. 테스트마다 문제가 선언한 세계로 초기 상태를 만들고 너비 우선으로 펼친다.
4. 끝난 상태마다 문제의 규칙 함수가 위반 문장을 돌려준다. 첫 위반에서 멈추고, 부모를 거슬러 올라가 반례 타임라인을 만든다.
5. 수치 단계는 통과한 설계를 정상 경로와 최악 경로로 한 번씩 돌려 점유 시간을 재고, 문항의 계산식에 넣는다.

## 3. 채점 엔진 v2

### 3.1 세계 모델

문제가 세계를 선언하고(`world`), 엔진은 자원 종류별 동작만 안다. DB 동작은 MySQL 8 InnoDB, REPEATABLE READ를 단순화했다.

| 자원 | 모델 |
|---|---|
| 서비스와 DB | 서비스마다 DB가 하나다. 흐름은 한 서비스에 속하고, 트랜잭션은 그 서비스 DB 안에서만 열린다 |
| 테이블 | 키별 행과 유니크 필드 |
| 일반 읽기 | 트랜잭션 안이면 첫 일반 읽기 시점의 스냅샷(내가 쓴 값은 보인다). 밖이면 최신 커밋 값 |
| 잠금 읽기, 변경, 삭제, 넣기 | 행 배타 잠금을 트랜잭션 끝까지 쥔다. 남이 쥐고 있으면 기다린다. 트랜잭션 밖이면 문장이 끝날 때 바로 커밋된다. 넣기는 키와 유니크 값에도 잠금을 건다 |
| 중복 키 | 그 문장만 실패하고 트랜잭션은 이어진다("중복이면" 갈래) |
| 데드락 | 잠금 대기가 고리를 이루면 마지막으로 기다리려던 쪽이 롤백되고 오류로 끝난다 |
| 외부 시스템 | 문제가 연산마다 결과 갈래와 장애 결과를 정의한다. 타임아웃은 보통 "실제로 반영됨"과 "안 됨" 두 갈래다 |
| 메시지 큐 | Kafka를 단순화했다. 토픽은 파티션 n개, 파티션마다 소비자 하나가 차례로 처리한다. 발행 결과는 성공, 실패, 타임아웃(써졌을 수도 아닐 수도). 키가 없으면 아무 파티션으로 간다. 소비 확인은 오프셋 커밋이다. 소비자가 죽으면 커밋한 오프셋부터 다시 받는다 |
| 캐시 | 읽기(있음, 없음), 쓰기(항상, 없을 때만, 버전이 더 클 때만), 삭제, 카운터 원자 증가. 명령 하나는 원자적이다 |
| 복제본 | 커밋된 쓰기가 커밋 순서대로 늦게 반영된다. 언제 반영되는지는 정해져 있지 않다 |
| 배경 흐름 | 요청이 끝난 뒤(after), 요청과 함께(concurrent), 소비까지 끝난 뒤(last) 돈다. 행마다 돌 수 있고(each), 서버 여러 대로 띄울 수 있다(instances). 요청이 끝난 뒤 정한 회차를 더 돈다 |
| 시간 | 테스트가 정한 사건(시각이 지남, 캐시 키 만료)을 "시간" 행위자가 아무 때나 순서대로 한 번씩 일으킨다 |
| 서버 다운 | 아무 블록 사이에서나. 열린 트랜잭션은 롤백된다. 요청은 응답을 받지 못하고, 배경 흐름은 다음 회차에 다시 돌고, 소비자는 커밋한 오프셋부터 다시 받는다 |

### 3.2 탐색

- 상태: DB와 복제본, 잠금, 외부 시스템, 캐시, 토픽과 오프셋, 행위자별(명령 위치, 트랜잭션, 읽은 값, 응답, 회차), 남은 장애 예산
- 다음 상태: 실행할 수 있는 행위자마다 한 걸음. 예산이 남아 있으면 다운과 장애 결과도 펼친다. 키 없는 발행은 파티션마다 갈린다.
- 너비 우선이라 처음 찾은 위반이 가장 짧은 반례다. 정상 걸음을 장애 걸음보다 먼저 큐에 넣어, 같은 길이면 장애가 적은 반례가 먼저 나오는 경향이 생긴다(엄밀한 보장은 아니다, 3.4).
- 상태를 직렬화해 방문 집합으로 중복을 지운다. 요청과 함께 도는 배경 흐름은 요청이 도는 동안의 회차에도 상한을 둬서 상태가 끝없이 늘지 않게 한다.
- 모든 행위자가 기다리며 멈추면 "진행 불가"로 실패한다.
- 상태가 25만 개를 넘으면 판정 없이 "한도 초과"를 돌려준다. 검수는 한도 초과를 실패로 본다.

### 3.3 점유 시간 측정

| 값 | 뜻 |
|---|---|
| T | 스레드 점유: 장애 없이 실행한 정상 경로의 전체 시간 |
| C | 커넥션 점유: 트랜잭션이 열려 있거나 DB 문장을 실행한 시간. 트랜잭션이 열린 동안의 외부 호출, 캐시 명령, 발행 시간도 들어간다 |
| L, Lk | 행 잠금 점유: 가장 오래 쥔 잠금(L)과 행별 값(Lk). 트랜잭션 밖 문장은 그 문장 시간 |
| W | 최악 수명: 외부 호출과 발행이 모두 타임아웃까지 걸린다고 볼 때 첫 행위자의 최대 시간 |
| n | 연산 횟수: DB 문장, 캐시 명령, 외부 연산별, 발행 |

- 블록별 지연과 계산 규칙은 문제의 수치 단계가 정한다. 문항 정답은 측정값을 받는 함수라서 설계가 바뀌면 정답이 바뀐다.

### 3.4 알려진 경계

엔진이 보지 못해서 틀린 설계가 통과할 수 있는 영역이다. N3에 따라 이 영역은 흐름 채점에 맡기지 않는다.

| 영역 | 이유 | 지금의 대응 |
|---|---|---|
| 외부 시스템이 타임아웃 뒤 늦게 반영하는 경우 | 타임아웃 갈래가 그 자리에서 확정된다 | 해설과 L4에서 다룬다 |
| 기다렸다 다시 시도하기 | 반복 블록이 없다 | 다른 갈래로 응답하거나 배경 흐름 회차에 맡긴다. 재시도 설계는 해설과 L4에서 다룬다 |
| 범위 조회, 합계 집계, 페이지 | 여러 행을 훑는 조회가 없다 | 행마다 도는 배경 흐름, 개수 세기, 행 하나에 모은 값으로 대신한다. 페이지 조회는 L5 객관식 |
| 갭 잠금, 잠금 대기 타임아웃 | 세계에 없다 | L5 객관식 |
| 서버 메모리(재시작하면 사라지는 값) | 세계에 없다 | 요청 값이나 행으로 표현한다 |
| 정확한 시각 간격 | 시간은 사건의 순서만 있다 | 시각이 필요한 판단은 요청 값으로 시각을 준다 |
| 소비자 리밸런스 | 세계에 없다 | 같은 메시지를 두 파티션에 넣어 동시 처리를 만든다 |
| 같은 길이 반례의 장애 수 순서 | 부모가 다른 경로끼리는 장애 수 순서가 뒤집힐 수 있다 | 판정에는 영향이 없고 표시 품질 문제다 |

v1 경계 가운데 "복구 흐름이 진행 중인 요청과 겹쳐 도는 경우"는 v2의 요청과 함께 도는 배경 흐름으로 해소했다. "여러 행, 여러 테이블, 메시지 큐, 캐시, 서비스 간 DB 분리"도 v2 세계에 들어왔다.

## 4. 데이터 계약

### 4.1 문제 파일

전체 계약의 원본은 작업 폴더의 `AUTHORING.md`다. 요지만 적는다.

| 필드 | 뜻 |
|---|---|
| `id`, `title`, `summary`, `order`, `types` | 식별자, 상황 한 줄, 홈 화면 순서, 이 문제가 다루는 유형([TYPES](TYPES.md) 이름) |
| `context`, `model` | 상황 설명, 채점 세계에서 단순화한 것(문제 화면에 보인다) |
| `world` | 테이블, 처음 행, 외부 시스템, 토픽, 캐시, 복제본 |
| `invariants(f, level, test)` | 끝난 상태를 받아 위반 문장 배열을 돌려준다. 안전 규칙과 진행 규칙을 둘 다 둔다 |
| `levels[]` | 단계 5개. `flow`(흐름 선언, 블록 재료, 규칙, 테스트, 힌트, 해설, 대표 오답), `quant`(측정 행위자, 지연, 계산 규칙, 문항), `choice`(내부 동작 객관식) |

블록: 트랜잭션 시작, 커밋, 읽기(일반, FOR UPDATE, 복제본), 개수 세기, 확인, 조건 갈래, 변경, 삭제, 넣기, 외부 호출, 메시지 발행, 소비 확인, 캐시 읽기, 쓰기, 삭제, 카운터 증가, 응답, 여기서 끝.

### 4.2 기록

브라우저 localStorage 키 `sysdesign-drill.v1`, 형식 `v: 2`

```text
{ v, settings: { mode, lockMin, theme },
  probs: { <문제 id>: { attempts: [ { startedAt, lv: { <단계 id>: 단계 기록 } } ] } } }
```

- 단계 기록: 연 시각, 통과 시각, 포기 여부, 힌트 사용 수, 제출 목록(제출마다 테스트별 결과), 편집 중인 흐름, 통과한 흐름, 수치 답, 서술 답, 말로 쓴 설계(`draft`), 설계를 마친 시각(`draftAt`), 설계 자가 판정(`draftSelf`)
- 설계 시간 = `draftAt - openedAt`, 옮기기 시간 = `solvedAt - draftAt`
- `attempts`의 원소 하나가 회차 하나다. "처음부터 다시 풀기"가 회차를 늘린다.
- v1(좌석 문제) 기록은 읽을 때 v2 블록 형식으로 옮긴다. 이전 엔진에서 암묵적이던 "0건이면 실패"는 갈래로 채워 넣는다(AD-12).
- 키는 추가만 한다. 뜻을 바꿔야 하면 새 키를 만든다. 형식을 깨야 하면 `v`를 올리고 읽을 때 옮긴다.

## 5. 결정 기록

### AD-1 채점은 상태 공간 전수 탐색으로 한다

- 상태: 채택(v1)
- 맥락: N1, N3. 설계의 맞고 틀림은 드물게 일어나는 실행 순서에서 갈린다.
- 결정: 행위자 실행 순서, 다운 지점, 외부 호출과 발행 결과를 너비 우선으로 모두 펼친다(모델 체킹).
- 고려한 대안

| 대안 | 버린 이유 |
|---|---|
| 정해 둔 시나리오 스크립트 | 출제자가 떠올린 순서만 본다. 다른 순서의 버그를 놓쳐 거짓 통과가 난다 |
| 무작위 시뮬레이션 | 실행할 때마다 결과가 달라질 수 있다(N1 위반). 반례가 길다 |
| AI 채점 | 사용자 결정으로 제외. 결정적이지 않다 |

- 결과: 범위 안에서는 빠짐이 없고 결정적이며 가장 짧은 반례가 나온다. 대신 상태가 폭발하므로 범위를 작게 묶는다(행위자 2~3명, 장애 예산 1~2, 배경 흐름 회차 2~3). 큰 범위의 버그도 대개 작은 범위에서 드러난다는 가정에 기댄다.

### AD-2 답은 기본 동작 블록 트리로 받는다

- 상태: 채택(v1), v2에서 블록 종류를 늘림
- 맥락: N7, N8. 서술은 기계가 채점할 수 없고, 코드는 원문 요구 2에 어긋난다.
- 결정: 블록은 기본 동작만 둔다(4.1). 패턴 이름은 블록 이름과 재료 이름에 쓰지 않는다.
- 고려한 대안

| 대안 | 버린 이유 |
|---|---|
| 패턴 블록 | 이름을 고르는 순간 답이 드러난다 |
| 구성도 | 기계로 채점할 수 없다 |
| 의사코드 | 코드에 가깝고, 파싱과 오류 안내 부담이 크다 |

- 결과: 답을 기계가 돌릴 수 있다. 블록 종류가 곧 세계 모델의 연산이라서 세계를 늘리면 블록도 는다. 단계마다 재료(팔레트)로 쓸 수 있는 블록과 값을 고른다.

### AD-3 DB 동작은 실제 제품 하나를 단순화해 고정한다

- 상태: 채택(v1)
- 맥락: N10. L5는 특정 DB의 내부 동작을 묻는다. 흐름 채점과 내부 질문이 같은 모델을 써야 앞뒤가 맞는다.
- 결정: MySQL 8 InnoDB, REPEATABLE READ를 기준으로 단순화한다. 세계의 모양(테이블, 서비스)은 문제가 선언하지만 동작은 이 기준을 따른다.
- 결과: 다른 DB의 동작 차이는 다루지 않는다.

### AD-4 장애는 테스트마다 예산으로 묶는다

- 상태: 채택(v1)
- 맥락: 장애를 무제한 허용하면 어떤 설계도 진행 규칙을 지킬 수 없고 상태도 폭발한다.
- 결정: 테스트가 다운될 수 있는 행위자, 외부 호출과 발행의 장애 결과, 장애 횟수 상한을 정한다.
- 결과: 테스트 정의가 곧 장애 모델이다. 입문 모드에서는 보이고, 실전 모드에서는 사용자가 이것을 세운다.

### AD-5 문제는 엔진과 분리하고, 출제 전에 대표 오답으로 검수한다

- 상태: 채택(v1)
- 맥락: N4, N15, N20.
- 결정: 문제 파일 하나에 상황, 세계, 규칙 함수, 단계, 테스트, 재료, 힌트, 해설, 대표 오답을 둔다. 대표 오답은 단계마다 3~5개, 면접에서 실제로 나오는 실수로 고르고, `fails`에 적은 테스트에서만 실패해야 한다.
- 결과: 대표 오답이 테스트의 구멍을 드러낸다. 규칙 함수는 자유로운 JS라서 실수가 섞일 수 있고, 그 실수도 검수가 잡아야 한다.

### AD-6 수치 정답은 사용자의 설계에서 계산한다

- 상태: 채택(v1)
- 맥락: N9, N11.

- 결과: 설계마다 정답이 다르다. 1에 가까운 비율은 ±10%로 가를 수 없어서 문항으로 쓰지 않는다.

### AD-7 HTML 한 파일, 서버 없음, 기록은 브라우저에

- 상태: 채택(v1)
- 결정: `build.py`가 엔진, 문제, 화면을 인라인 스크립트로 묶는다(모듈을 쓰면 file://에서 막힌다). GitHub Pages로 내보낸다.
- 결과: 어디서나 열린다. 기기 간 기록 공유는 없다. 모범 답이 HTML 안에 들어 있어 소스 보기로 볼 수 있다. 사용자가 한 명이고 스스로 보지 않는 것으로 받아들인다.

### AD-8 원본 코드를 이 저장소로 옮긴다

- 상태: 제안(PRD D4)
- 맥락: 원본(`src/`, `app/`, `test/`, `build.py`, `AUTHORING.md`)은 저장소 밖 작업 폴더에 있다. 이 문서가 가리키는 코드가 저장소에 없고, 원본의 변경 이력도 없다.
- 결과: 모범 답은 이미 `index.html`에 들어 있어서 원본을 공개해도 새로 드러나는 것은 없다.

### AD-9 엔진 v2: 고정된 세계를 선언형 자원의 조합으로 바꾼다

- 상태: 채택(v2, 2026-10-21)
- 맥락: v1 세계(행 하나, 결제 하나)는 엔진 코드에 박혀 있어 정합성 문제의 절반(서비스 간 유실, 중복 메시지)을 낼 수 없었다.
- 결정: 문제가 세계를 선언하고 엔진은 자원 종류별 동작만 안다(3.1).
- 고려한 대안: v1 엔진에 테이블과 큐를 덧붙인다. 문제마다 엔진 분기가 늘고, 문제와 엔진의 분리(AD-5)가 깨진다.
- 회귀 기준: 좌석 문제를 새 세계 선언으로 옮긴 뒤 검수 결과(대표 오답별 실패 테스트, 수치 정답)가 v1과 같았다.
- 결과: 유형 28개(흐름 채점 22, 수치 중심 6)를 문제 22개로 냈다([TYPES](TYPES.md)).

### AD-10 반례 표시: 바뀐 상태를 "한 일" 칸 아래에 붙인다

- 상태: 채택(v2)
- 맥락: 자원이 늘면 상태 열이 390px 폭을 넘는다.
- 결정: 걸음마다 그 걸음에서 바뀐 자원만 "한 일" 칸 아래에 붙이고, 처음 상태는 접어 둔다. 배경 흐름이 같은 일을 되풀이한 회차는 한 줄로 접는다.

### AD-11 숙달 집계를 (문제, 유형) 단위로 바꾼다

- 상태: 제안(PRD D1)
- 맥락: 지금은 테스트 하나가 표본 하나이고 모든 회차를 합친다.
- 결정(제안): 표본은 (문제, 유형)이다. 체화 판정에는 첫 회차만 쓰고, 재풀이 회차는 복습 지표로 따로 보여 준다.
- 결과: 기록 형식은 바꾸지 않는다. 제출마다 테스트별 결과가 이미 남아 있어서 집계만 바꾸면 된다.

### AD-12 갈래가 비면 다음 블록으로 넘어간다 (변경 0건, 넣기 중복 포함)

- 상태: 채택(v2)
- 맥락: v1에서는 변경이 0건이면 암묵적으로 실패로 끝났다. 영향받은 행 수를 확인하지 않는 실수는 실무에서 흔한데 문제로 낼 수 없었다.
- 결정: 변경, 삭제는 1건/0건, 넣기는 들어감/중복 갈래를 갖는다. 모든 갈래는 비면 다음 블록으로 넘어간다. "확인" 블록만 어긋나면 실패로 끝난다.
- 결과: "0건을 확인하지 않음"이 대표 오답이 된다. v1 기록은 읽을 때 0건 갈래에 실패 응답을 채워 옮긴다.

### AD-13 블록 편집기는 문제의 재료로 그린다

- 상태: 채택(v2)
- 맥락: 문제마다 테이블, 값, 외부 연산이 다르다. v1 편집기는 좌석 문제에 묶여 있었다.
- 결정: 단계의 흐름마다 재료(쓸 수 있는 블록, 테이블과 키, 비교 대상, 바꿀 값, 넣기와 발행 목록, 캐시 키와 값)를 선언하고, 화면은 그 재료로만 선택지를 만든다. 답을 가르는 선택은 기본값 없이 고르게 한다.
- 결과: 화면 코드를 건드리지 않고 문제를 더한다. 모범 답과 오답의 값이 재료에 없으면 화면 점검이 "고르지 않은 칸"으로 잡는다.
- v2.1: 드롭다운 대신 문장 속 칩으로 바꾸고, 칩을 누르면 아래에서 선택판이 올라온다. 바꿀 값과 조건은 고른 것만 보이고 "＋"로 더한다. 빈 갈래는 한 줄로 접고, 블록 메뉴로 이동, 복사, 잘라내기, 붙여넣기를 한다.

### AD-14 시간은 연속 시각이 아니라 사건으로 둔다

- 상태: 채택(v2)
- 맥락: 만료, 정기 실행, 구간 마감 같은 유형은 시간이 지나야 생긴다.
- 결정: 테스트가 사건 목록(시계 행 바꾸기, 캐시 키 만료)을 정하고, 시간 행위자가 아무 때나 순서대로 일으킨다. 배경 흐름은 시간 사건이 다 일어난 뒤에 남은 회차를 돌게 할 수 있다.
- 고려한 대안: 매 걸음 시계가 한 칸씩 가는 논리 시계. 상태가 시계 값만큼 늘어 폭발한다.
- 결과: "언제 일어나든"을 빠짐없이 본다. 정확한 시각 간격은 다루지 못해 요청 값으로 시각을 준다(3.4).

### AD-15 문제 작성은 지침과 세 가지 점검으로 묶는다

- 상태: 채택(v2)
- 맥락: 문제 22개를 여러 작성자가 나눠 썼다. 품질과 답 비노출을 한 기준으로 맞춰야 한다.
- 결정: `AUTHORING.md`를 작성 계약으로 두고, 문제마다 검수(validate), 화면 점검(browser-check), 답 노출 점검(leak-check)을 통과해야 낸다. 작성자는 자기 문제 파일만 고치고, 엔진에 필요한 기능은 보고해 엔진 쪽에서 더한다.
- 결과: 작성 중 드러난 엔진의 빈틈(읽은 값으로 계산해 덮어쓰기, 행별 잠금 시간, 배경 흐름 회차 상한, 서버 여러 대, 시간 사건)을 엔진에 넣고 기존 문제를 다시 검수했다.

### AD-16 답 입력을 두 단계로 나눈다: 말로 먼저, 블록으로 옮겨 채점

- 상태: 채택(v2.1, PRD D3)
- 맥락: 블록 하나하나를 고르는 입력은 모범 답 하나에 조작이 중앙값 23번, L2는 50~100번 들었다. 그래서 "소요 시간"이 설계를 떠올리는 시간보다 클릭하는 시간을 더 쟀다. 면접에서 하는 말하기 연습도 없었다.
- 결정: 흐름 단계를 열면 먼저 설계를 3~5줄로 적는다. 다 적어야 블록 편집기가 열린다. 설계 시간과 옮기기 시간을 따로 남긴다. 해설에서 내 글과 모범 답("면접에서 말로 하면")을 나란히 놓고 스스로 판정한다.
- 고려한 대안

| 대안 | 버린 이유 |
|---|---|
| 의사 SQL 텍스트와 자동완성 | 키보드에서는 빠르지만 휴대폰에서 느리고, 코드에 가까워 원문 요구 2와 부딪힌다 |
| 자유 서술을 AI가 채점 | 서술형 AI 채점을 하지 않기로 한 결정과 어긋난다 |

- 결과: 채점은 그대로 블록으로 하고, 숙달 속도는 설계 시간으로 잰다. 이 기능 전에 시작한 단계는 설계 단계를 건너뛴다.

### AD-17 중급 모드는 문제 전체의 재료를 합쳐 보여 준다

- 상태: 채택(v2.1)
- 맥락: 재료(팔레트)를 단계마다 필요한 것 위주로 추려 주면 재료 목록이 힌트가 된다. 반례를 보고 고르기를 바꾸는 반복으로 풀릴 수 있다.
- 결정: 중급에서는 그 문제의 모든 흐름 단계 재료를 같은 흐름끼리 합친다. 입문은 지금처럼 단계별 재료를 쓴다.
- 결과: 엔진은 어떤 재료 조합이든 세계 규칙대로 돌리므로 채점은 바뀌지 않는다. 중급에서는 고를 칸이 늘어난다.
