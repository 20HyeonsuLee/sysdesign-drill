# ARD: 시스템 설계 꼬리질문

| 항목 | 값 |
|---|---|
| 상태 | 초안, 2026-10-21 |
| 함께 읽을 문서 | [PRD](PRD.md): 문제, 근본 요구(N), 기능(F), 결정 필요(D) |

- [PRD](PRD.md)의 근본 요구를 채우는 구조와, 그 구조를 고른 이유를 적는다.
- 결정은 AD 번호로 남긴다. 뒤집을 때는 지우지 않고 상태를 바꾼다.
- 모범 답과 해설은 이 문서에 쓰지 않는다.

## 1. 아키텍처 동인

PRD 요구 가운데 구조를 정하는 것만 추린다.

| ID | 품질 속성 | 기준 | 출처 |
|---|---|---|---|
| Q1 | 채점 건전성 | 세계 모델과 장애 예산 안의 실행 순서를 빠짐없이 탐색한다. 표본 추출을 하지 않는다 | N2, N3 |
| Q2 | 결정성 | 같은 입력이면 같은 결과와 같은 반례가 나온다 | N1 |
| Q3 | 반례 최소성 | 가장 짧은 반례를 돌려준다. 길이가 같으면 장애가 적은 쪽이 먼저다 | N5 |
| Q4 | 채점 시간 | 휴대폰에서 단계 하나를 기다림 없이 채점한다. 테스트당 상태 상한 25만 개 | N19 |
| Q5 | 표현력과 비노출 | 정답을 여러 갈래로 표현할 수 있고, 블록이 답을 알려 주지 않는다 | N4, N8 |
| Q6 | 문제 추가 비용 | 엔진을 건드리지 않고 문제 파일 하나로 추가한다. 엔진을 늘려도 기존 문제 검수가 그대로 통과한다 | N15, N20 |
| Q7 | 실행 환경 | 서버 없이 HTML 한 파일로 동작하고 file://로도 열린다 | N18 |
| Q8 | 기록 보존 | 버전이 바뀌어도 브라우저에 남은 기록을 읽는다 | N14 |

v1 측정 (2026-10-21, 검수 스크립트)

- 좌석 문제 전체 검수(모범 답 4개, 대표 오답 10개, 수치 2단계) 41ms
- 테스트당 상태 수 최대 242개. 상한 25만 개까지 여유가 크고, 이 여유를 엔진 v2의 세계 확장에 쓴다.

## 2. 구성

```text
src/engine.js          채점 엔진: 블록 트리 컴파일, 상태 공간 탐색, 점유 시간 측정
src/problems/<id>.js   문제: 상황, 세계 초기값, 규칙 함수, 단계, 테스트, 힌트, 해설, 대표 오답
app/                   화면: 템플릿, 스타일, 블록 편집기, 반례 표, 기록
test/validate.js       검수: 모범 답 전부 통과, 대표 오답은 기대한 테스트에서만 실패
build.py               엔진, 문제, 화면을 인라인 스크립트로 묶어 HTML 한 파일을 만든다
index.html             빌드 결과. GitHub Pages가 내보낸다
```

- 지금 이 저장소에는 `index.html`과 문서만 있다. 원본은 저장소 밖 작업 폴더에 있다(AD-8).

채점 흐름

1. 사용자가 블록 트리를 쌓는다. 단계에 따라 요청 흐름 하나, 또는 요청 흐름과 복구 흐름 둘이다.
2. 엔진이 블록 트리를 점프가 있는 명령 배열로 컴파일한다. 외부 호출 블록은 결과마다 점프 대상을 갖는다.
3. 테스트마다 초기 상태(행 값, 행위자, 장애 예산)를 만들고 너비 우선으로 펼친다.
4. 끝난 상태마다 문제의 규칙 함수가 위반 문장을 돌려준다. 첫 위반에서 멈추고, 부모를 거슬러 올라가 반례 타임라인을 만든다.
5. 수치 단계는 통과한 설계를 정상 경로와 최악 경로로 한 번씩 돌려 점유 시간을 재고, 문항의 계산식에 넣는다.

## 3. 채점 엔진 v1

### 3.1 세계 모델

MySQL 8 InnoDB, REPEATABLE READ를 단순화했다.

| 대상 | 모델 |
|---|---|
| DB | 행 하나. 커밋된 값과 트랜잭션별 쓰기 버퍼 |
| 일반 읽기 | 트랜잭션 안이면 첫 읽기 시점의 스냅샷(내가 쓴 값은 보인다). 밖이면 최신 커밋 값 |
| 잠금 읽기, 변경 | 행 배타 잠금을 잡고 최신 커밋 값을 본다. 다른 트랜잭션이 쥐고 있으면 기다린다 |
| 트랜잭션 밖 잠금 읽기 | 문장이 끝나면 잠금이 풀린다 |
| 응답 시 열린 트랜잭션 | 성공 응답과 처리 중 응답이면 커밋, 실패 응답이면 롤백 |
| 외부 시스템 | 결제(PG) 하나. 승인, 조회, 취소. 같은 주문번호는 같은 결제다 |
| 외부 타임아웃 | "실제로 반영됨"과 "반영 안 됨" 두 갈래로 펼친다 |
| 서버 다운 | 아무 블록 사이에서나. 열린 트랜잭션은 롤백되고 응답은 나가지 않는다 |
| 복구 흐름 | 요청이 모두 끝나거나 죽은 뒤 3회차 돈다. 회차 도중 다운되면 다음 회차에 다시 돈다 |

### 3.2 탐색

- 상태: DB 값, 잠금, 외부 시스템 상태, 행위자별(명령 위치, 트랜잭션, 읽은 값, 응답), 남은 장애 예산
- 다음 상태: 실행할 수 있는 행위자마다 한 걸음. 예산이 남아 있으면 그 행위자의 다운과 외부 호출의 장애 결과도 펼친다.
- 너비 우선이라 처음 찾은 위반이 가장 짧은 반례다.
- 정상 걸음을 장애 걸음보다 먼저 큐에 넣는다. 같은 길이면 장애가 적은 반례가 먼저 나오는 경향이 생긴다. 엄밀한 보장은 아니다(3.4).
- 상태를 직렬화해 방문 집합으로 중복을 지운다.
- 모든 행위자가 잠금을 기다리며 멈추면 "진행 불가"로 실패한다.
- 상태가 25만 개를 넘으면 판정 없이 "한도 초과"를 돌려준다. 검수는 한도 초과를 실패로 본다.

### 3.3 점유 시간 측정

| 값 | 뜻 | 재는 법 |
|---|---|---|
| T | 스레드 점유 | 장애 없이 혼자 실행한 정상 경로의 전체 시간 |
| C | 커넥션 점유 | 그중 트랜잭션이 열려 있거나 DB 문장을 실행한 시간 |
| W | 최악 수명 | 외부 호출이 모두 타임아웃 끝까지 걸린다고 보고, 요청 하나가 살아 있을 수 있는 최대 시간 |

- 블록별 지연(ms)과 계산 규칙은 문제의 수치 단계가 정한다.
- 문항 정답은 `{C, T, W}`를 받는 함수다. 설계가 바뀌면 정답이 바뀐다.

### 3.4 알려진 경계

엔진이 보지 못해서 틀린 설계가 통과할 수 있는 영역이다. N3에 따라 이 영역은 흐름 채점에 맡기지 않는다.

| 영역 | 이유 | 지금의 대응 |
|---|---|---|
| 복구 흐름이 진행 중인 요청과 겹쳐 도는 경우 | 복구 흐름은 요청이 다 끝난 뒤에만 돈다 | 일부를 L4 수치 문항으로 묻는다. 엔진 v2에서 해소(AD-9) |
| 외부 시스템이 타임아웃 뒤 늦게 반영하는 경우 | 타임아웃 갈래가 그 자리에서 확정된다 | 없음. 엔진 v2에서 해소(AD-9) |
| 여러 행, 여러 테이블, 메시지 큐, 캐시, 서비스 간 DB 분리 | 세계에 없다 | 이 영역의 문제는 v2 전까지 내지 않는다 |
| 같은 길이 반례의 장애 수 순서 | 부모가 다른 경로끼리는 장애 수 순서가 뒤집힐 수 있다 | 판정에는 영향이 없고 표시 품질 문제다. (길이, 장애 수) 순 탐색으로 바꿀지 결정 필요 |

## 4. 데이터 계약

### 4.1 문제 파일

공통

| 필드 | 뜻 |
|---|---|
| `id`, `title`, `summary`, `context` | 식별자와 상황 설명 |
| `row`, `rows`, `fields` | 세계 초기값과 필드 정의(값 목록, 화면 이름) |
| `invariants(f, level, test)` | 끝난 상태 `f`를 받아 위반 문장 배열을 돌려준다 |
| `levels[]` | 단계. `kind`는 `flow`, `quant`, `choice` 중 하나 |

`flow` 단계

| 필드 | 뜻 |
|---|---|
| `flows` | 사용자가 쌓는 흐름. `req`(요청), `rec`(복구) |
| `palette` | 쓸 수 있는 블록과 값 |
| `rules` | 화면에 보이는 규칙 문장. 실전 모드에서는 숨긴다 |
| `tests[]` | `id`, `name`, `tags`(실패 유형), `actors`, `rows`, `crash`(다운될 수 있는 행위자), `faults`(외부 호출별 장애 결과), `budget`(장애 예산), `desc` |
| `hints[]` | 3단계 힌트 |
| `answer` | 모범 답 흐름(1개 이상), 해설, 이어질 꼬리질문, 사례 링크 |
| `validation[]` | 대표 오답 흐름과 `fails`(실패해야 할 테스트 id 목록) |

`quant` 단계: `from`(이어받는 단계), `lat`, `worstLat`(블록별 지연), `givens`, `rulesText`(계산 규칙), `questions[]`(`answer(m)`이 정답 계산), `essay`, `refs`

`choice` 단계: `questions[]`(보기와 정답, `tag`), `refs`

### 4.2 기록

브라우저 localStorage 키 `sysdesign-drill.v1`

```text
{ v, settings: { mode, lockMin, theme },
  probs: { <문제 id>: { attempts: [ { startedAt, lv: { <단계 id>: 단계 기록 } } ] } } }
```

- 단계 기록: 연 시각, 통과 시각, 포기 여부, 힌트 사용 수, 제출 목록(제출마다 테스트별 결과), 편집 중인 흐름, 통과한 흐름, 수치 답, 서술 답
- `attempts`의 원소 하나가 회차 하나다. "처음부터 다시 풀기"가 회차를 늘린다.
- 키는 추가만 한다. 뜻을 바꿔야 하면 새 키를 만든다. 형식을 깨야 하면 `v`를 올리고 읽을 때 옮긴다.

## 5. 결정 기록

### AD-1 채점은 상태 공간 전수 탐색으로 한다

- 상태: 채택(v1)
- 맥락: N1, N3. 설계의 맞고 틀림은 드물게 일어나는 실행 순서에서 갈린다.
- 결정: 행위자 실행 순서, 다운 지점, 외부 호출 결과를 너비 우선으로 모두 펼친다(모델 체킹).
- 고려한 대안

| 대안 | 버린 이유 |
|---|---|
| 정해 둔 시나리오 스크립트 | 출제자가 떠올린 순서만 본다. 다른 순서의 버그를 놓쳐 거짓 통과가 난다 |
| 무작위 시뮬레이션 | 실행할 때마다 결과가 달라질 수 있다(N1 위반). 반례가 길다 |
| AI 채점 | 사용자 결정으로 제외. 결정적이지 않다 |

- 결과: 범위 안에서는 빠짐이 없고 결정적이며 가장 짧은 반례가 나온다. 대신 상태가 폭발하므로 범위를 작게 묶는다(행위자 3명 이하, 장애 예산 1~2, 복구 3회차). 큰 범위의 버그도 대개 작은 범위에서 드러난다는 가정에 기댄다.

### AD-2 답은 기본 동작 블록 트리로 받는다

- 상태: 채택(v1)
- 맥락: N7, N8. 서술은 기계가 채점할 수 없고, 코드는 원문 요구 2에 어긋난다.
- 결정: 블록은 트랜잭션 시작, 커밋, 읽기(잠금 여부는 사용자가 고른다), 확인, 조건부 변경, 외부 호출(결과별 갈래), 응답, 회차 끝이다. 패턴 이름은 블록 이름에 쓰지 않는다.
- 고려한 대안

| 대안 | 버린 이유 |
|---|---|
| 패턴 블록 | 이름을 고르는 순간 답이 드러난다 |
| 구성도 | 기계로 채점할 수 없다 |
| 의사코드 | 코드에 가깝고, 파싱과 오류 안내 부담이 크다 |

- 결과: 답을 기계가 돌릴 수 있다. 블록 종류가 곧 세계 모델의 연산이라서 세계를 늘리면 블록도 는다. 블록이 많아지면 편집 부담이 커지므로 단계마다 `palette`로 쓸 수 있는 블록을 고른다.

### AD-3 세계는 실제 제품 하나를 단순화해 고정한다

- 상태: 채택(v1)
- 맥락: N10. L5는 특정 DB의 내부 동작을 묻는다. 흐름 채점과 내부 질문이 같은 모델을 써야 앞뒤가 맞는다.
- 결정: MySQL 8 InnoDB, REPEATABLE READ를 기준으로 단순화한다.
- 고려한 대안: 격리 수준을 고르는 추상 DB. 일반적이지만 L5와 이어지지 않는다.
- 결과: 다른 DB의 동작 차이는 다루지 않는다.

### AD-4 장애는 테스트마다 예산으로 묶는다

- 상태: 채택(v1)
- 맥락: 장애를 무제한 허용하면 어떤 설계도 진행 규칙을 지킬 수 없고 상태도 폭발한다.
- 결정: 테스트가 다운될 수 있는 행위자, 외부 호출별 장애 결과, 장애 횟수 상한을 정한다. 외부 타임아웃은 반영 여부에 따라 두 갈래로 펼친다.
- 결과: 테스트 정의가 곧 장애 모델이다. 입문 모드에서는 보이고, 실전 모드에서는 사용자가 이것을 세운다.

### AD-5 문제는 엔진과 분리하고, 출제 전에 대표 오답으로 검수한다

- 상태: 채택(v1)
- 맥락: N4, N15, N20. 문제를 늘려도 엔진을 건드리지 않아야 하고, 테스트의 구멍을 출제 전에 찾아야 한다.
- 결정: 문제 파일 하나에 상황, 초기값, 규칙 함수, 단계, 테스트, 힌트, 해설, 대표 오답을 둔다. 검수는 모범 답이 전부 통과하는지, 대표 오답이 `fails`에 적은 테스트에서만 실패하는지 본다. 대표 오답은 단계마다 3~5개, 면접에서 실제로 나오는 실수로 고른다.
- 고려한 대안: 규칙을 선언형으로 적기. 실전 모드에서 사용자가 세운 규칙과 비교하기 쉽지만 v1에는 과하다(6절).
- 결과: 대표 오답이 테스트의 구멍을 드러낸다. 규칙 함수는 자유로운 JS라서 실수가 섞일 수 있고, 그 실수도 검수가 잡아야 한다.

### AD-6 수치 정답은 사용자의 설계에서 계산한다

- 상태: 채택(v1)
- 맥락: N9, N11. 꼬리질문은 내 설계를 이어받는다.
- 결정: 통과한 L2 설계를 3.3의 방식으로 재고 문항 식에 넣는다. 계산 규칙은 문제에 적는다. ±10%면 정답이다.
- 고려한 대안: 고정 정답. 내 설계와 상관없는 숫자를 외우게 된다.
- 결과: 설계마다 정답이 다르다. 모범 답 기준 수치는 검수가 출력한다.

### AD-7 HTML 한 파일, 서버 없음, 기록은 브라우저에

- 상태: 채택(v1)
- 맥락: N18, N19.
- 결정: `build.py`가 엔진, 문제, 화면을 인라인 스크립트로 묶는다(모듈을 쓰면 file://에서 막힌다). GitHub Pages로 내보낸다. 기록은 localStorage에 둔다.
- 결과: 어디서나 열린다. 기기 간 기록 공유는 없다. 모범 답이 HTML 안에 들어 있어 소스 보기로 볼 수 있다. 사용자가 한 명이고 스스로 보지 않는 것으로 받아들인다.

### AD-8 원본 코드를 이 저장소로 옮긴다

- 상태: 제안(PRD D4)
- 맥락: 원본(`src/`, `app/`, `test/`, `build.py`)은 저장소 밖 작업 폴더에 있고, 저장소에는 빌드 결과만 올린다. 이 문서가 가리키는 코드가 저장소에 없고, 원본의 변경 이력도 없다.
- 결정(제안): 원본을 이 저장소로 옮긴다. Pages는 지금처럼 빌드 결과 `index.html`을 내보낸다.
- 결과: 모범 답은 이미 `index.html`에 들어 있어서 원본을 공개해도 새로 드러나는 것은 없다.

### AD-9 엔진 v2: 고정된 세계를 선언형 자원의 조합으로 바꾼다

- 상태: 제안
- 맥락: v1 세계(행 하나, 결제 하나)는 엔진 코드에 박혀 있다. 이 세계로는 정합성 문제의 절반(서비스 간 유실, 중복 메시지)을 낼 수 없다. 3.4의 경계도 여기서 생긴다.
- 결정(제안): 문제가 세계를 선언한다. 세계는 자원의 집합이다. 자원 종류마다 상태, 연산(블록), 연산별 결과 갈래, 장애 결과, 반례 표시 방법을 엔진에 등록한다.

| 자원 | 상태 | 연산(블록) | 장애 |
|---|---|---|---|
| 테이블 | 키별 행, 유니크 제약 | 키로 읽기(잠금 여부 선택), 삽입("중복이면" 갈래), 조건부 변경 | |
| 서비스 DB | 테이블 묶음. 트랜잭션은 한 서비스 DB 안에서만 열린다 | 트랜잭션 시작, 커밋 | 서비스 단위 다운 |
| 외부 시스템 | 요청 키별 상태 | 문제가 정한다 | 거절, 타임아웃(반영됨, 안 됨), 늦은 반영 |
| 메시지 큐 | 파티션별 메시지 목록, 소비자별 위치 | 발행, 소비 흐름(메시지마다 실행), 소비 확인 | 발행 실패, 발행 결과 모름, 중복 전달, 순서 역전, 소비 도중 다운 |
| 주기 흐름 | 회차 | 회차 끝 | 회차 도중 다운 |

- 행위자는 요청 흐름, 소비 흐름, 주기 흐름 세 종류다. 주기 흐름은 요청과 겹쳐 돌 수 있다. 복구 흐름은 주기 흐름의 한 경우가 된다.
- 고려한 대안: v1 엔진에 테이블과 큐를 덧붙인다. 문제마다 엔진 분기가 늘고, 문제와 엔진의 분리(AD-5)가 깨진다.
- 회귀 기준: 좌석 문제를 새 세계 선언으로 옮긴 뒤에도 검수가 그대로 통과한다.
- 위험: 상태 폭발. 테스트당 행위자와 메시지 수에 상한을 두고, 같은 일을 하는 행위자는 대칭으로 묶어 줄이고, 상태 직렬화를 정규형으로 만든다. 검수는 테스트별 상태 수를 출력해 출제자가 범위를 보게 한다.

### AD-10 반례 표시를 바뀐 자원 위주로 다시 짠다

- 상태: 제안
- 맥락: AD-9로 행과 메시지가 늘면 지금의 한 줄 표가 390px 폭을 넘는다.
- 결정(제안): 반례 한 걸음마다 그 걸음에서 바뀐 자원만 보여 주고, 전체 상태는 펼쳐 보기로 둔다.

### AD-11 숙달 집계를 (문제, 유형) 단위로 바꾼다

- 상태: 제안(PRD D1)
- 맥락: 지금은 테스트 하나가 표본 하나이고 모든 회차를 합친다. 문제 하나의 첫 제출로 한 유형의 표본이 5개 넘게 생길 수 있고, 재풀이 회차가 기억으로 통과율을 올린다.
- 결정(제안): 표본은 (문제, 유형)이다. 그 유형이 붙은 테스트나 문항이 첫 제출에서 하나라도 실패하면 그 표본은 실패다. 체화 판정에는 첫 회차만 쓰고, 재풀이 회차는 복습 지표로 따로 보여 준다.
- 결과: 기록 형식은 바꾸지 않는다. 제출마다 테스트별 결과가 이미 남아 있어서 집계만 바꾸면 된다.
